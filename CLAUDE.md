# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project

Towards the Unknown: a turn-based tactics roguelite on a tile grid, built with **Unity 6000.6.0f1** (see `ProjectSettings/ProjectVersion.txt`; the README's 2020.3 version is outdated), URP, Wwise for audio, Steamworks and the Discord Game SDK. Work happens on the `dev` branch; `main` is the default branch.

Game code lives entirely in `Assets/Scripts` and compiles into `Assembly-CSharp` (no asmdef), grouped by domain: `Core` (turns, action queue, input, `GameAssets`), `Entities` (player and enemies), `Combat` (artifacts, effects, statuses, VFX), `Inventory`, `Map` (generation, rooms, tiles), `UI`, `Audio`, `Platform` (Steam, Discord), `Localization`, `Visuals`, `DevTools` and `Utility`. Data assets live in `Assets/Data`. `Assets/Plugins`, `Assets/ThirdParty` and `Assets/Wwise` are vendored and should not be refactored. There are no automated tests.

Build scenes, in order: `Assets/Scenes/Game/0-PreMenu`, `1-Menu`, `2-Game`. `Scenes/Archives` and `Scenes/Tests` are old or debug scenes.

## Compiling outside the editor

`dotnet build Assembly-CSharp.csproj` works once Unity has regenerated the project files (Edit > Preferences > External Tools > Regenerate project files, or opening the project). The generated `.csproj` gets stale after files are moved or deleted and then fails with `CS2001` (missing source file). Its references use `Library/ScriptAssemblies`, so Unity must have compiled the project at least once. Compiling does not validate scene/prefab wiring: check that in the editor.

## Unity-specific pitfalls in this codebase

- A MonoBehaviour's class name must match its file name, otherwise the component silently fails to load in scenes and prefabs.
- Scenes and prefabs reference scripts by GUID (the `.meta` file) and fields by name. Deleting a script, renaming a serialized field (without `[FormerlySerializedAs]`) or renaming a method used by a UnityEvent/animation event (`m_MethodName` / `functionName` in `.unity`/`.prefab`/`.anim`) breaks data silently. Grep the assets before removing or renaming anything.
- Artifacts and enemy patterns are assets (`ArtifactData` in `Assets/Data/Artifacts`, `EnemyPatternData` in `Assets/Data/EnemyPatterns`). An artifact's asset name is its ID: it keys the localized texts, the player animator state and the Wwise event (`Player_<ID>`); a pattern's asset name is its Wwise event. Renaming an asset requires renaming those too. Effects are `[SerializeReference]` `CombatEffect` subclasses: renaming or moving one breaks the assets using it unless it gets a `[MovedFrom]` attribute.
- Texts use the Unity Localization package: string tables `Artifacts`, `UI` and `Entities` in `Assets/Localization/Tables`, read through the `Localization` class. Artifact keys are `<ID>.Title`, `.Description`, `.Effects`, `.Range` and `.Cooldown`; entity keys are prefab names. `Effects`, `Range` and `Cooldown` are smart strings with named values: each `CombatEffect` names its own (`{minDamage}`, `{maxDamage}`, `{minSelfDamage}`, `{armor}`, `{heal}`, `{distance}`, `{attackUpTurns}`...), `Range` gets `{minRange}` to `{maxArea}` and `Cooldown` gets `{value}`. `<D>` and `<B>` tags are replaced by the highlight color. UI texts keep positional `{0}` placeholders formatted by the callers. The startup language comes from Steam (`SteamLocaleSelector`), French otherwise.
- Wwise events are posted by string (`AkUnitySoundEngine.PostEvent`), often built from names (`"Player_" + artifact ID`, enemy pattern asset names, `<Enemy>_Footstep`).
- Nothing is loaded from `Resources` by path except `GameAssets` (`Resources/GameAssets`), which only holds assets needed by code that has no object to own them (today the hit VFX). Reference new assets from a serialized field on the prefab or scene object that uses them (the minimap, the HUD, `Map`, `DraregAI`, `Collectable` and `TreasureSpawnPoint` do); use `GameAssets` only as a last resort, and never add `Resources.Load` calls.
- Don't look objects up by name, path or tag (`GameObject.Find`, `FindGameObjectWithTag`) nor with `FindAnyObjectByType` in gameplay code. Reference objects of the same prefab or scene from a serialized field; objects spawned at runtime (rooms, enemies, HUD items) and actions reach the player, the UI and the map through `GameScene` (`GameScene.Player`, `.UI`, `.Map`), and the UI's menus, fade, minimap and panels through `ChangeUI`. Don't link the scene's prefab instances to each other with scene overrides (the test scenes would miss them): the player, `UI.prefab` (which holds the pause and results UIDocuments) and `Gameplay.prefab` (turn system, camera and its shake) reach each other through `GameScene` or events. `GameScene` and `TurnSystem.Instance` are the only lookups (`FindAnyObjectByType`; the older `FindObjectOfType` is deprecated in this Unity version).
- The `Awake` order between objects is not guaranteed: don't read another object's fields initialized in its own `Awake` from an `Awake` (the `PlayerTurn.Inventory` and `.Stats` properties resolve on first use for that reason).
- Input goes through the Input System: `Core/Input/Controls.inputactions` (maps `Gameplay`, `Inventory`, `Menus`, `UI`, `Debug`) and its generated `Controls` class, owned by the static `GameInput`. Subscribe to an action's `performed`/`canceled` in `OnEnable` and unsubscribe in `OnDisable` rather than polling in `Update`; don't use the legacy `Input` class. The `Debug` map is only enabled in the editor and development builds. The EventSystems use an `InputSystemUIInputModule` bound to the `UI` map, and the main camera's `PhysicsRaycaster` (Enemy layer) sends pointer events to enemies.
- Prefer events to per-frame polling and to gameplay calling the UI: `EntityStats.StatsChanged` (and the static `EntityStats.AnyDamageTaken`, used by the HUD's `DamageIndicators`), `PlayerStats.EnergyChanged`, `PlayerTurn.SelectedArtifactChanged` (skills bar highlight), `TurnSystem.TurnOrderChanged` (timeline), `GameEvents.RunEnded` (results screen), `ActionManager.QueueFree` / `WhenFree`, `Room.newTileHovered` / `tileClicked`.

## Architecture

**Turn flow.** `TurnSystem` (singleton, `TurnSystem.Instance`) holds the ordered list of `EntityTurn`s: the player is always first, then enemies in spawn order. Nothing is polled per frame: the player acts through input events, and `EnemyAI` plays its turn as steps (move, attack, end turn) chained with `ActionManager.WhenFree`, each step checking `TurnSystem.IsCurrentTurn`. Combat starts in `CheckForCombatStart()` when enemies are registered, and ends when only the player remains (`EndCombat` waits for the action queue to empty, then `Room.OnRoomClear` spawns the reward).

**Action queue.** Everything that takes time or must happen in order (damage, movement, status effects, deaths, waiting for attack animations, ending a turn) is a `GameAction` (`Core/Turns/Actions`) pushed to the static `ActionManager` queue and processed in `Update` (move with `Time.deltaTime`). `OnStart()` runs once when the action reaches the head of the queue (start animations, VFX and timers there, not in the constructor), then `Apply()` runs every frame until the action sets `isDone`; coroutines run on the manager through `ActionManager.Run`. An exception in an action is logged and the action dropped. `ActionManager.IsBusy` blocks player input, and the `ActionManager.QueueFree` event fires when the queue empties (used to leave attack mode, to end combat and to chain enemy turn steps).

**Entities.** Each combatant GameObject combines `EntityStats` (HP, armor, damage multipliers, status effects), `EntityTurn` (turn hooks), `TacticsMove` (tile pathing and movement via `MoveAction`) and `TacticsAttack`. The player versions are `PlayerStats` (energy used for both moving and casting), `PlayerTurn` (MOVE/ATTACK state, number keys select artifacts), `PlayerMove` and `PlayerAttack`. Every standard enemy prefab is a variant of `Entities/Enemies/Enemy.prefab` (GreatNanuko through `Nanuko.prefab`; not Drareg, whose components are subclasses), which holds the shared components, layer, tag and `TileWatcher` child; a variant only adds its model and overrides its values. Create new enemies as variants of it; references to enemies point to their `EnemyAI` component (`EnemySpawnPoint.enemyPrefab`). Enemies use `EnemyAI`, configured on the enemy prefab with an `EnemyPatternSet`: the distance to keep from the target and an ordered list of `EnemyPatternData` assets (`Assets/Data/EnemyPatterns`; the first usable one is cast, the first one also drives movement). `DraregAI` is the two-phase boss, with two random first-phase sets, a second-phase set and an ultimate.

**Artifacts** (player skills, `Combat/Artifacts`). An `ArtifactData` ScriptableObject, edited with Odin, defines cost, uses per turn, cooldown, target tag, range and optional area (`TileSearchConfig`), VFX, inventory shape and two lists of `CombatEffect`s (`Combat/Effects`): cast effects applied once with the caster as target, and effects applied to each target. `Artifact` is its runtime instance (`data.CreateArtifact()`), holding the cooldown and remaining uses. Effects only queue actions (damage, armor, heal, stat modifier, move). Status effects (`StatModifierStatus` subclasses) change the damage multipliers; applying the opposite status cancels both. Enemy patterns use the same effects, ranges and VFX; `EnemyPattern` is their runtime instance.

**Tiles.** Tiles are instances of `Assets/Prefabs/LevelDesign/Tile.prefab`, which nests the selection overlay (`TileOverlay`) and references it from a serialized field; per-tile mesh, material, collider, decoration children and `TransitionTile` are overrides. Build new rooms from this prefab, never from raw models with a `Tile` component added. `Tile` components form the grid; neighbours are found by physics overlap in `Awake` and stored in `lAdjacent` (keyed by world direction). `TileSearch` subclasses (circle/BFS and line searches) combine tile constraints (walkable, empty, line of sight) to compute ranges and paths. `Room` raises `newTileHovered` / `tileClicked` events that the player movement, attack and deploy phases subscribe to.

**Map.** `Assets/Prefabs/LevelDesign/Map.prefab` holds the `Map` component and the exit VFX; each scene uses a variant of it from `LevelDesign/Maps` that adds its generation. Every room prefab is a variant of `LevelDesign/Room.prefab` (through `CombatRoom.prefab` or `TreasureRoom.prefab` for those types), which holds the shared settings such as the tile model list; `RoomSet` assets and `FixedMapGeneration` reference the rooms' `Room` component, so converting a room into a variant requires remapping those references. `Map` asks a `MapGeneration` component (`RandomMapGeneration`, or `FixedMapGeneration` for hand-made layouts) for a grid of `RoomInfo`. `RandomMapGeneration` picks room prefabs from a `RoomSet` asset (`Assets/Data/Rooms`), listing the rooms of each type. Combat rooms carry several `EnemySpawnLayout`s tagged with a difficulty; the generator splits a total difficulty across combat rooms. Moving onto a `TransitionTile` fades out, destroys the current room and instantiates the adjacent one (`Room.SetExits` removes the exits leading nowhere and adds the exit VFX, shown while the room has no combat); `PlayerDeploy` subclasses place the player (combat rooms let the player pick a deploy tile first). `RoomInfo` remembers visited rooms and unclaimed loot.

**UI.** The menus and the HUD use UI Toolkit; the minimap, fade and inventory are still UGUI canvases, to be migrated. `Hud` (`Hud/Hud.uxml`) builds the status (`StatusPanel`), status effects (`StatusEffectsPanel`), timeline (`TimelinePanel`), skills (`SkillsBar`), hovered enemy info (`EntityInfoPanel`, shown by the enemies' `InfoEntity`) and damage indicators (`DamageIndicators`) from the player, the turn order and the events; gameplay sets its action button through `GameScene.UI.Hud.EnterActionState` / `EnterDeployState`, and `Tile` ignores the pointer over a UI Toolkit element (`Hud.IsPointerOver`). UI Toolkit assets live in `Assets/UI`: `PanelSettings` (1920x1080 reference, sorted above the canvases) with the `Theme.tss` theme importing `Styles/Common.uss` (colors, fonts, buttons, sliders, screens) and `Styles/Hud.uss`, the screens in `Menus` (`PauseMenu`, `Results` and `MainMenu`, the last two sharing the `Options` template bound by `OptionsView`) and the `SlantedBlur` backdrop filter in `Filters`. A screen is shown by adding the `open` class. Every screen script calls `MenuScreen.Setup`, which plays the button sounds, uppercases the `caps` texts (USS has no text-transform) and attaches `CutShape` to the `cut` elements (call `CutShape.AttachAll` on the elements created later): it draws the game's shape (rectangle with corners cut at 45°, up to parallelograms and diamonds) as the element's background from USS custom properties (`--cut-size`, `--cut-corners`, `--fill-color`, `--line-color`, `--line-width`, `--backdrop-blur`) and blurs the backdrop with `SlantedBlur`, which leaves the cut corners sharp. Blur only what is behind a panel with the backdrop filter, never the whole screen (no depth of field). Texts are bound to the string tables in UXML (`<l:LocalizedString property="text" table="UI" entry="..."/>`). `GameFlow` loads the scenes.

**Inventory.** Artifacts are placed in a Tetris-style grid (`TetrisInventory*`). The skill bar lists the artifacts in the player inventory. The starting artifacts are set on `InventoryManager` in `Player.prefab`, and treasures draw from `ArtifactPool` assets (`Assets/Data/ArtifactPools`); a `Collectable` opens a chest grid to drag artifacts from.
